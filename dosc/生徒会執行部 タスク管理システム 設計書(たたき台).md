# 生徒会執行部 タスク管理システム 設計書(たたき台)

2026年10月21日時点｜

## 1. 目的と前提

- **目的**: 各班のタスクとスケジュールを一か所で確認でき、役割に応じて指示・管理・承認ができるようにする
- **利用者**: 執行部 11〜30人。PCブラウザが中心
- **アカウント**: 学校管理下のGoogleアカウント。管理者に外部アプリの許可を取るのは難しい見込み
- **期間**: R8年度　すぐに使う
- **保守**: 生徒1~数名

## 2. 実現方式

スプレッドシート + Google Apps Script(HTML画面のWebアプリ)で作ります。

- 学校ドメイン内で完結するため、外部アプリとしての許可申請を避けられる見込みです。学校アカウントでApps Scriptの作成・実行ができることは確認済みです
- **ログイン**: Webアプリを「ドメイン内のユーザーのみ」に公開し、メンバー表に登録されたメールアドレスだけが使えるようにします
- **データ**: 新しい「システム用シート」を作り、既存シートはそのまま残します
- **権限チェック**: 画面でボタンを隠すだけでなく、サーバー側(Apps Script)でも必ず確認します
- **弱点**: メール送信やカレンダー更新は、デプロイしたアカウントの名義で行われます。そのアカウントが使えなくなると止まるため、管理者を複数にして引き継ぎ手順を用意します

## 3. 役割と権限

役割は「人 × 班」で持ちます。兼任している人は、班ごとに役割が変わります。会長・副会長は全班に対する上位権限を持ち、人ごとに個別設定します。

| 操作 | 会長・副会長 | 班長 | 班員 |
| --- | --- | --- | --- |
| 全班のタスクの閲覧・コメント | ○ | ○ | ○ |
| タスクの作成 | ○ | ○(自班) | 「提案」として作成 |
| タスクの割り当て | 全班 | 自班のみ | 不可 |
| 他班への依頼 | 直接割り当て | 会長・副会長に依頼 | 不可 |
| 提案・完了報告・期限変更の承認 | 代理で承認可 | 自班(1段階目) | 不可 |
| 「重要」の指定と最終承認 | ○ | 不可 | 不可 |
| メンバー・班・役割の変更 | ○ | 不可 | 不可 |

**承認まわりのルール**

- 班長自身のタスクの完了・期限変更は自己承認でよい
- ただし、会長・副会長が「重要」に指定したタスクは、班長自身の分でも会長・副会長の承認が入る
- 会長・副会長自身のタスクは、会長・副会長同士で相互承認する
- 会長・副会長は、班長の代理としていつでも承認できる

**システム管理者**(生徒)は、役職とは別の「全体権限」として扱います。メンバー管理、行事一覧の入力、データの修正ができ、タスクの承認には関わりません(要確認)。

## 4. タスクの流れ

1. **提案中**: 班員が作成したタスクの初期状態。班長が承認すると正式なタスクになる(班長・会長・副会長が作成した場合は「未着手」から始まる)
2. **未着手 → 進行中**: 担当者が更新する
3. **完了報告**: 担当者が報告すると、班長の承認待ちになる
4. **最終承認待ち**: 「重要」に指定されたタスクのみ。会長・副会長の承認待ちになる
5. **完了**

- **差し戻し**: 承認者が戻すと「進行中」に戻り、担当者に通知される
- **期限変更申請**: 担当者が新しい期限と理由を申請し、完了報告と同じ承認ルートを通る

**タスクの項目**: タイトル、説明、担当班、担当者(複数可)、期限、優先度(高・中・低)、ステータス、「重要」フラグ、関連資料リンク(複数可)、サブタスク(チェックリスト)、コメント

## 5. データ設計(システム用シート)

| シート | 主な列 |
| --- | --- |
| メンバー | メールアドレス(キー)、名前、有効/無効 |
| 班 | 班ID、班名 |
| 所属 | メールアドレス、班ID、役割(班長/班員) |
| 全体権限 | メールアドレス、全体役割(会長/副会長/システム管理者) |
| タスク | タスクID、タイトル、説明、担当班、優先度、期限、ステータス、重要フラグ、作成者、作成・更新日時 |
| 担当者 | タスクID、メールアドレス(複数担当を表現する) |
| サブタスク | タスクID、内容、完了 |
| コメント | タスクID、投稿者、内容、日時 |
| 資料リンク | タスクID、URL、資料名 |
| 申請 | タスクID、申請者、新しい期限、理由、状態、承認者 |
| 行事一覧 | 日付、開始・終了時刻、タイトル、メモ、カレンダーのイベントID |
| 操作ログ | 日時、操作者、操作内容、対象 |

## 6. 既存シートとの関係と入力ルール

既存シート(R8\_前期生徒会本部)は残し、役割を次のように整理します。

- **資料まとめ**: 資料の台帳として使う。タスクに資料リンクを追加すると、システムが自動で1行追加する
- **各班タブ**: 班内のメモ、下書き、アイデア出し(インスタ班の投稿管理表など)に使う。期限と担当者が決まったらシステムに登録する、というルールを1つだけ決める
- **月別カレンダータブ**: 行事一覧に移行し、廃止するか過去の記録として残す
- **デジタル意見箱**: 今回は対象外。今のフォームとシートのまま
- **Home**: 定例予定(班長会、定例会、全体会)は行事一覧に繰り返しで登録する

**資料まとめの入力ルール(新規)**

1. 編集者・監督者は、学校のメールアドレスで統一する
2. ファイル列は、URLをそのまま入れる(表示名リンクはやめる)
3. タイプ・詳細・ステータスのプルダウンは維持し、システムの選択肢と同じにする
4. 掲載日は、システムが登録時に自動入力する
5. 「タスクID」列を1つ追加する
6. 同じURLは重複して登録しない(システムが確認する)

**個人情報**: 班タブの名簿には学籍番号やメールアドレスが含まれます。システム用シートの共有は管理者と会長・副会長に限り、開発中のテストにはダミーデータを使います。

## 7. カレンダー連携

- **行事予定**: 既存スプレッドシートに新しく作る「行事一覧」タブに、会長とシステム管理者が入力する。システムが共有カレンダーへ反映する(シート → カレンダーの一方向)
- **共有カレンダーは書き込み専用**にする。執行部の共有権限は「予定の表示のみ」とし、カレンダー側の直接編集による上書きを防ぐ
- **タスクの期限**: 同じ共有カレンダーに、終日予定として「【期限】タイトル(班名)」の形で反映する
- 行事一覧の各行にイベントIDを保持し、変更・削除もカレンダーに反映する

## 9. 画面構成

- **ホーム(ログイン後の最初の画面)**: 全班の進捗一覧。班別にステータスごとの件数と、期限超過のタスクが分かる
- **自分のタスク**: 担当しているタスクを期限順に表示
- **タスク詳細**: 説明、担当者、サブタスク、資料リンク、コメント、承認ボタン
- **承認待ち**: 自分が承認すべき提案・完了報告・期限変更申請
- **カレンダー**: 期限と行事の月表示
- **管理**: メンバー・班・役割の編集(会長・副会長、システム管理者のみ)

## 10. 開発の進め方

| 段階 | 時期の目安 | 内容 |
| --- | --- | --- |
| 第1段階 | 〜2週目 | ログイン、メンバー・班・役割の管理、タスクの作成・割り当て、全班の閲覧とコメント、班員の提案と班長の承認、権限制御、資料リンクの自動登録 |
| 第2段階 | 3週目 | Gmail通知(動き、前日、期限超過、週次まとめ) |
| 第3段階 | 4週目 | 行事一覧の共有カレンダー反映、タスク期限の反映 |
| 第4段階 | 1か月以降 | 完了報告、2段階承認、差し戻し、期限変更申請 |

- 第1段階の完了は、担当者が自分で「完了」にできる簡易版にします。ステータスは最初から承認を見越して設計するので、第4段階で作り直しは起きません
- 本番のシートを触る前に、**コピーしたシートで開発とテスト**を行います
- スクリプトの編集権限は管理者2〜3名で共有し、デプロイするアカウントの引き継ぎ手順を決めておきます

## 12. 第1版(MVP)の仕様【確定。「10. 開発の進め方」より優先】

最優先は「各班のタスクの期限と進め方の可視化」です。第1版は、これだけを確実に使える状態にします。

**画面**

- **全班の進捗一覧(ホーム)**: 班ごとに、ステータス別の件数と期限超過のタスクが分かる
- **班別の一覧**: タスク名、担当者、開始日、期限、ステータスを表で見る
- **タイムライン**: 開始日から期限までを横軸で見る(ガントチャート風)。班ごとに行をまとめる
- **タスク詳細**: 説明、担当者、開始日、期限、ステータス、資料リンクの一覧と追加
- **会議用の全班表示**: 文字を大きくして、定例会や班長会で画面を映しても読みやすくする

**権限(第1版の簡易版)**

| 操作 | 会長・システム管理者 | 班長 | 班員 |
| --- | --- | --- | --- |
| 全班の閲覧 | ○ | ○ | ○ |
| タスクの作成・編集 | ○(全班) | ○(自班) | 不可 |
| ステータスの更新 | ○(全班) | ○(自班) | 自分が担当のタスクのみ |
| 資料の追加 | ○ | 所属する班のタスク | 所属する班のタスク |
| メンバー・班・役割の管理 | ○ | 不可 | 不可 |

- 兼任者は、所属するすべての班で、その班での役割が適用される
- タスクの入力は、会長とシステム管理者が基本。班長も自班のタスクを追加できる

**タスクの項目(第1版)**

タイトル、説明、担当班、担当者(複数可)、**開始日(必須)**、**期限(必須)**、ステータス(未着手・進行中・完了)、優先度、資料リンク

**資料の追加**

- タスク詳細で、URLと資料名を入れ、タイプと詳細をプルダウンで選んで追加する
- 追加すると、既存シートの「資料まとめ」に自動で1行追加される(編集者はメールアドレス、掲載日は自動入力、タスクIDを記録)
- 同じURLはすでに登録されていれば追加しない

**第1版では作らないもの(後の段階で追加)**

班員の「提案」と承認、完了報告・2段階承認、期限変更申請、「重要」の指定、Gmail通知、行事一覧と共有カレンダーの同期。後から足せるよう、データの持ち方(重要フラグ、作成者、更新日時、操作ログなど)は最初から合わせておく。

**第1版で追加確認したいこと**

1. 副会長にタスクの作成・編集の権限を与えるか(いまは会長とシステム管理者のみ)
2. コメントとサブタスクを第1版に入れるか
3. 会長は、全班のタスクに資料を追加できてよいか
4. 期限超過や、期限が近いタスクをどう目立たせるか(色分けなど)

## 13. プロジェクト(追加機能)

プロジェクトは、行事や企画のまとまりです。中にタスクが含まれ、プロジェクトごとの進捗が見えるようにします。

**ルール**

- 1つのプロジェクトは、基本的に1つの班が担当する。タスクの担当班は、プロジェクトの担当班が初期値になる
- タスクは、プロジェクトに属さなくてもよい(単発タスクも作れる)
- 進捗率は「完了したタスクの数 ÷ プロジェクト内の全タスクの数」で計算する。単発タスクは対象外。タスクが0件のプロジェクトは「タスクなし」と表示する
- 進捗率は画面を開くたびに計算するので、後から重みづけ方式などに変えても、データの作り直しは要らない

**画面**

- **プロジェクト一覧**: 班ごとにまとめ、進捗バー、期間、完了数/全タスク数を表示する
- **プロジェクト詳細**: そのプロジェクトのタスク一覧、タイムライン、進捗を表示する
- **全班の進捗一覧(ホーム)**: 班ごとのプロジェクトの進捗も合わせて表示する(仮)

**データ**

- 「プロジェクト」シートを追加する: プロジェクトID、名前、説明、担当班、責任者、開始日、終了日、状態
- 「タスク」シートに「プロジェクトID」列を追加する(空欄可)

**確認中**: プロジェクトの作成・編集の権限、プロジェクトに持たせる項目、第1版に含めるかどうか

## 14. プロジェクトの確定事項(13の「確認中」を確定)

- **作成・編集**: 会長・システム管理者(全班)と、班長(自班のプロジェクトのみ)。班員は閲覧のみ
- **項目**: プロジェクト名、担当班、説明・目的、開始日、終了日、状態(進行中・完了・保留)。責任者の項目は持たせない
- **開発の順番**: 第1版に含める。第1版の範囲は「12. 第1版(MVP)の仕様」に、プロジェクト一覧とプロジェクト詳細を加えたもの
- **「プロジェクト」シートの列**: プロジェクトID、名前、説明・目的、担当班、開始日、終了日、状態(「13. データ」から責任者を除く)

**第1版の権限表への追加**

| 操作 | 会長・システム管理者 | 班長 | 班員 |
| --- | --- | --- | --- |
| プロジェクトの閲覧 | ○ | ○ | ○ |
| プロジェクトの作成・編集 | ○(全班) | ○(自班) | 不可 |

**仮の扱い(要確認)**

- プロジェクト一覧は、初期表示を「進行中」のみとし、「完了」「保留」は切り替えて見る
- タスクの期間がプロジェクトの開始日〜終了日からはみ出したときは、画面に警告を出す

## 15. 第1版から既存シートとの連携を外す(12の資料まわりを変更)

- 第1版では、既存シート(R8\_前期生徒会本部)の読み書きや連携は行わない。「資料まとめ」への自動追加も作らない
- 資料の追加は、システム内で完結させる。タスク詳細で資料名とURLを入れて追加し、システム用シートの「資料リンク」に保存して、タスク詳細に一覧で表示する
- 資料の項目は、資料名、URL、追加者、追加日時。タイプ・詳細は持たせない(資料まとめの分類に合わせるためのものだったため)
- 同じタスクに同じURLを重複して追加しないチェックは残す
- システム用シートは、新しいスプレッドシートとして独立して作る。メンバー・班の初期データはそこに直接入力する(必要なら既存シートから手作業で転記する)
- 既存シートとの連携(資料まとめへの書き込み、行事一覧の同期など)は、第2段階以降で改めて検討する
- 「10. 開発の進め方」の「資料の連携」は、「資料の追加(システム内)」に置き換える
